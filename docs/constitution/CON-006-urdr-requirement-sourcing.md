# CON-006 — URDR 요구사항 소싱 원칙

## CON-006.1 경험의 계승

Moirai의 요구사항은 URDR의 목표 문서, 코드, 계약, 테스트, phase 기록, 실패 재현과 실제 사용 경험에서 적극적으로 소싱한다.

## CON-006.2 해결책의 비자동 계승

URDR의 기존 기능, 데이터 구조, 프로토콜과 운영 절차는 요구사항의 증거이지 Moirai가 그대로 계승해야 하는 정답이 아니다.

## CON-006.3 문제 중심 추출

URDR의 각 장치는 그것이 풀려고 했던 문제, 효과, 부작용을 분리해 검토한 뒤 Moirai의 요구사항으로 재정의한다.

## CON-006.4 추적 가능성

URDR에서 소싱한 중요한 요구사항의 근거는 분석 기록이나 구현 작업에서 추적할 수 있어야 한다. 이 근거 자료는 Moirai 규범의 의미를 대신하지 않으며 URDR의 변경이 Moirai 명세를 암묵적으로 변경해서는 안 된다.

## CON-006.5 반복 경로 경계

초기의 단순한 근본문제 하나만 해결한 뒤 같은 문제를 다시 발견하며 URDR와 동일한 경로를 반복하지 않는다. 이미 발견된 운영 요구를 초기 설계 범위에 함께 고려한다.

## CON-006.6 독립적인 재명세

URDR는 분석 및 구현 참고자료이지 Moirai 명세의 일부가 아니다.

URDR에서 발견한 문제, 제약과 유효한 설계 원리는 Moirai의 용어와 문맥으로 다시 정의한다. Moirai의 헌법, 비즈니스 요구사항과 기술 명세는 URDR를 읽지 않아도 이해하고 구현할 수 있는 자기완결적인 문서여야 한다.

`URDR와 동일하게`, 특정 URDR 파일·함수·화면에 대한 링크 또는 기존 명칭만으로 요구사항이나 기술 결정을 대신해서는 안 된다. 실제 구현 작업에서 URDR의 코드를 참고하라는 지시는 별도의 작업 지시로 줄 수 있으며 규범 명세에는 포함하지 않는다.
